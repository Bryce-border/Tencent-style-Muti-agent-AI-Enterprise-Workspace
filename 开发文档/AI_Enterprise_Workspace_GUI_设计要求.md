# AI Enterprise Workspace —— GUI 设计要求

## 1. 产品定位

AI Enterprise Workspace 是一个以**总智能体（Master Agent）为唯一主要入口**的 AI 工作空间。

产品不强调“用户去使用不同 Agent”，而强调：

> **用户只需要描述目标，总智能体负责理解、规划、协调、执行、检查和交付。**

整体交互参考 **Codex / DeepSeek Harness / AI IDE** 类型产品，但面向企业复杂任务与长内容生产场景。

核心交互链路：

```text
用户提出目标
    ↓
Master Agent 理解需求
    ↓
生成预计输出方案
    ↓
用户查看 / 修改 / 批准
    ↓
Agent 自动规划与执行
    ↓
实时展示任务进度
    ↓
生成最终 Artifact
    ↓
用户继续追问 / 修改
    ↓
Memory 记录用户偏好
    ↓
下一次会话自动复用
```

---

## 2. GUI 总体设计原则

### 2.1 Conversation-first

整个产品以“会话”作为最核心的工作单位，而不是传统企业软件中的功能菜单。

用户打开产品后首先看到的是对话窗口，而不是 Dashboard、Task Center 或 Agent 列表。

### 2.2 能力隐藏

Agent、Planner、Router、Memory、Reviewer、Tool 等属于系统内部能力，默认不主动暴露。

用户只需要知道：

- AI 正在理解什么
- AI 准备输出什么
- AI 当前执行到哪一步
- 最终产生了什么结果

需要深入了解时，再展开“执行详情”。

### 2.3 默认简洁，按需展开

主界面保持大量留白和较低的信息密度。

复杂信息采用：

- 折叠卡片
- Drawer / Side Panel
- Tab
- “查看详情”
- “查看预计输出”
- “查看执行过程”

实现**默认简单、高级用户可深入**的体验。

### 2.4 任务围绕结果，而不是围绕 Agent

用户真正需要的是：

- 文档
- 报告
- PPT
- Excel
- 分析结论
- 项目方案
- 代码

因此最终结果以 **Artifact（交付物）** 为核心展示形式。

---

# 3. 整体页面结构

建议第一版只保留 4 个主要区域：

```text
AI Enterprise Workspace
│
├── 会话 / Home
├── 知识库
├── 记忆
└── 设置
```

其中使用频率最高的页面只有：

> **Home / Conversation**

不单独设置以下一级导航：

- Assistant
- Tasks
- Agents
- Reports
- Data Analysis
- Meetings
- Documents

这些都是总智能体背后的能力或任务结果，应在会话中呈现。

## 4.1 页面定位

主界面是整个产品最重要的页面。

用户所有复杂工作都从这里开始，并且最终结果也回到这里。

整体结构：

```text
┌──────────────┬─────────────────────────────────────────────┐
│              │                                             │
│  会话列表     │                  对话工作区                  │
│              │                                             │

│              │                                             │
│ 最近会话      │   需求理解                                  │
│              │   预计输出                                  │
│ 旅游项目      │   用户确认                                  │
│ CRM PRD       │   执行进度                                  │
│ 销售分析      │   Artifact                                  │
```

支持：

# 6. 新建会话后的首屏

首页中央区域应该突出一个大型任务输入框。

示例：

```text
今天想完成什么？

描述你的目标，剩下的交给 AI

┌───────────────────────────────────────┐
│ 我想做一个旅游全栈项目，包括前端、后端、数据库、AI 推荐功能…… │
│                                       │
│                         📎   +    ↑   │
└───────────────────────────────────────┘

常用：
[项目方案] [需求文档] [数据分析] [市场分析]
```

重点：

- 不展示 Agent 选择器
- 不要求用户选择模型
- 不要求用户选择任务类型
- 不要求用户理解内部流程

用户直接描述目标即可。

# 7. Master Agent 对话交互

用户输入复杂需求以后，Master Agent 不立即长篇生成最终结果。

第一步应该是**理解并生成预计输出方案**。

例如用户输入：

> 我要做一个旅游全栈项目。

AI 应回复类似：

```text
我理解你的目标是：

构建一个完整的旅游全栈项目方案，覆盖产品、前端、后端、数据库和 AI 推荐能力。

根据你的需求，我预计输出：

📑 项目开发方案

预计规模：
- 一级章节：10 个
- 二级章节：35 个左右
- 预计字数：15,000 ～ 20,000 字
- 输出格式：Markdown
- 预计包含：3 张架构 / 流程图

目录：
1. 项目概述
2. 产品需求
3. 用户角色
4. 产品功能设计
5. 系统架构
6. 前端设计
7. 后端设计
8. 数据库设计
9. AI / Agent 设计
10. 开发计划与验收标准

是否需要修改输出方案？

[查看 / 修改]    [直接批准]
```

---

# 8. “预计输出”卡片

预计输出是产品的核心中间产物。

在真正执行前，Master Agent 必须尽可能明确：

- 输出类型
- 输出结构
- 目录
- 预计篇幅
- 预计章节数量
- 输出格式
- 风格
- 是否需要图表
- 是否使用历史模板
- 是否存在需要用户确认的关键点

## 8.1 用户操作

提供两个主要动作：

```text
[直接批准]
[查看 / 修改]
```

### 直接批准

按照当前预计方案进入执行阶段。

### 查看 / 修改

打开预计输出编辑面板。

预计输出应该支持轻量级修改，而不是让用户重新输入完整 Prompt。

```text
│ 篇幅：15,000 ～ 20,000 字           │
│ 格式：Markdown                      │
│ 风格：专业 / 详细                   │
│                                    │
│ 章节结构                            │
│ ☑ 项目概述                          │
│ ☑ 产品需求                          │
│ ☑ 系统架构                          │
│ ☑ 前端设计                          │
│ ☑ 后端设计                          │
│ ☑ 数据库设计                        │
│ ☑ Agent 设计                        │
│ ☑ 开发计划                          │
│                                    │

│ [________________________________] │
│                                    │
```

用户也可以直接在聊天框中说：

> 增加竞品分析，删除部署部分，数据库设计扩展到 3000 字。

Master Agent 只更新预计输出方案，不需要重新规划整个任务。

# 10. 自动批准 Auto Approve

自动批准是产品个性化能力的重要组成部分。

## 10.1 作用

用户可以设置：

> **符合我的历史偏好时，自动批准预计输出方案。**

例如用户长期习惯：

```text
语言：中文
文档风格：专业
详细程度：详细
格式：Markdown
默认包含：架构图、数据库设计、验收标准
```

当下一次用户再次提出类似需求时，系统可以自动复用这些偏好。

## 10.2 自动批准状态

建议提供一个轻量的顶部开关：

```text
自动批准：○ / ●
```

并明确说明：

> 仅当预计输出与已保存的用户偏好高度一致时自动批准。

用户始终可以点击：

```text
[查看预计输出]
```

检查 AI 即将采用的方案。

# 11. 用户 Memory 设计

Memory 页面独立存在，但不应该频繁打扰主流程。

Memory 的重点不是“保存聊天记录”，而是保存**经过用户确认的长期偏好和工作规则**。

建议分类：

```text
User Memory
├── 输出偏好
├── 文档格式
├── 语言习惯
├── 篇幅习惯
├── 常用模板
└── 用户明确保存的规则
```

可扩展：

```text
Workspace Memory
Task Memory
Agent Memory
```

## 11.1 Memory 示例

```text
用户偏好

文档默认语言：中文
默认风格：专业
默认详细程度：详细
默认格式：Markdown
默认包含：验收标准

[编辑]
```

## 11.2 Memory 对后续会话的影响

用户之前确认：

> 技术方案默认详细、中文、Markdown，并包含架构图和数据库设计。

之后用户新建会话：

> 帮我设计一个电商全栈项目。

系统自动读取 Memory，并显示：

```text
根据你的历史偏好，我预计：

- 中文
- 详细版
- Markdown
- 包含架构图
- 包含数据库设计
- 包含开发计划

[查看预计输出]  [直接批准]
```

# 12. 长文档生成交互

系统不得采用“一次 Prompt 生成全部长文档”的方式作为唯一策略。

对于需求文档、项目开发方案、市场报告等长内容，采用：

```text
需求理解
   ↓
生成目录
   ↓
用户确认
   ↓
章节规划
   ↓
分章节生成
   ↓
共享上下文 / Document Memory
   ↓
一致性检查
   ↓
Reviewer
   ↓
必要时重新生成章节
   ↓
最终组装
```

用户界面不需要展示所有内部技术细节，只显示业务级进度。

例如：

```text
正在生成项目方案……

✓ 项目背景
✓ 产品需求
✓ 用户角色
✓ 系统架构
● 前端设计
○ 后端设计
○ 数据库设计
○ AI / Agent 设计
○ 质量检查
```

# 13. 执行详情

执行过程中默认隐藏内部 Agent。

提供按钮：

```text
[查看执行详情]
```

点击后展开 Drawer：

```text
Master Agent
 ├── Planner ✓
 ├── Knowledge Agent ✓
 ├── Data Agent ✓
 ├── Document Agent ●
 └── Reviewer ○
```

可进一步展示：

- Agent 状态
- 当前任务
- 并行任务
- Tool 调用
- 错误 / 重试
- 耗时

该区域属于高级信息，不应该破坏主页面的简洁性。

# 14. Artifact 产物展示

最终输出直接回到当前会话。

不跳转到单独的“Task 页面”。

示例：

```text
已完成。

📄 旅游全栈项目开发方案

20,138 字
12 个章节
3 张架构图

┌────────────────────────────┐
│ 📄 travel-project-plan.md  │
│                            │
│ [打开] [导出 PDF] [导出 Word] │
└────────────────────────────┘
```

支持的 Artifact 类型：

- Markdown
- PDF
- Word / DOCX
- PPT / PPTX
- Excel / XLSX
- 图片 / 图表
- 代码文件
- 压缩包

用户可以继续在当前会话中修改：

> 把数据库设计再细化。

系统基于当前上下文继续处理。

# 15. 知识库页面

知识库是独立页面，但设计也应该保持简洁。

核心目标：

> **让用户知道自己的知识文件是否已经被正确解析，以及 RAG 是如何使用这些内容的。**

页面：

```text
知识库

[上传文件]   [搜索]

我的知识文件

📁 产品资料
 ├── PRD.pdf
 ├── 产品手册.docx
 └── API 文档.md

📁 企业制度
 ├── HR 制度.pdf
 └── 报销制度.docx
```

点击文件后显示：

- 文件名称
- 文件类型
- 文件大小
- 页数
- 解析状态
- Chunk 数量
- Embedding 状态
- 更新时间

知识库需要支持查看具体分块。

界面建议：

```text
┌────────────────┬────────────────────────────┐
│ Chunk 列表      │ Chunk #027                 │
│                │                            │
│ #001           │ 标题：用户登录              │
│ #002           │                            │
│ #003           │ 用户登录支持手机号、微信…  │
│ ...            │                            │
│ #027 ←         │ Metadata                   │

│                │ section: 用户系统            │

│                │ embedding: ✓                │
└────────────────┴────────────────────────────┘
```

```text

```

```text
原始文档
   ↓

   ↓
Chunk 切分
   ↓
Embedding
   ↓
向量检索
```

# 19. 视觉设计要求

整体视觉参考现代 AI Harness / AI IDE，而不是传统 ERP / OA。

关键词：

> **极简、轻量、专业、低干扰、高信息质量。**

建议：

- 浅色背景
- 白色内容卡片
- 低饱和蓝色作为主要强调色
- 细边框
- 轻阴影
- 8～12px 圆角
- 大面积留白
- 清晰的文字层级
- 少量图标
- 动画克制

避免：

- 大量彩色 Dashboard 卡片
- 过多 KPI
- 复杂侧边菜单
- Agent 图标墙
- 大量传统表格
- 强烈渐变
- 过度装饰

# 21. 核心用户体验闭环

整个 GUI 最终应围绕以下闭环展开：

```text
ASK
用户描述目标
    ↓
PLAN
Master Agent 分析需求
    ↓
PREVIEW
展示预计输出 / 目录 / 篇幅 / 格式
    ↓
APPROVE
用户批准或修改
    ↓
EXECUTE
Master Agent 协调专业 Agent 执行
    ↓
REVIEW
系统检查结果
    ↓
DELIVER
输出 Artifact
    ↓
REFINE
用户继续对话修改
    ↓
REMEMBER
保存用户长期偏好
    ↓
REUSE
后续会话自动复用
```

产品核心可以浓缩为一句话：

> **Ask → Plan → Approve → Execute → Deliver → Remember**

# 22. 第一版 GUI 开发优先级

第一版不建议一次实现全部功能。

## P0：核心闭环

1. 会话列表
2. Master Agent 对话
3. 预计输出卡片
4. 查看 / 修改预计输出
5. 批准执行
6. 执行进度
7. Artifact 展示
8. 当前会话继续追问

## P1：个性化

1. 自动批准
2. User Memory
3. 历史偏好复用
4. 输出模板

# 23. GUI 设计最终目标

这个 GUI 不应该让用户感觉：

> “我正在操作一个复杂的 Multi-Agent 系统。”

而应该让用户感觉：

> **“我告诉 AI 我要完成什么，它先告诉我准备怎么做，我确认后，它替我把这件事完整做完。”**

所有复杂的 Agent 协作、Memory、RAG、数据库问数、长文档拆分、Reviewer、工具调用，都应该隐藏在这条简单的用户体验之下。

**产品的简洁来自于复杂度被系统吸收，而不是项目本身功能简单。**
