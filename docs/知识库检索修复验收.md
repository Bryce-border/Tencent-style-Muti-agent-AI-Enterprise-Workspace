# 知识库检索修复验收

日期：2026-09-14。范围：R2 现有文本知识库的检索、引用与历史报告展示修复，不表示 R3 文件中心已完成。

## 原因与修复

| 原问题 | 当前行为 |
| --- | --- |
| kNN 对任何问题都返回前 5 条 | 设置余弦相似度下限，允许零命中；只保留与最强有效结果分差不超过窗口的候选 |
| 同一段报销内容以多个文档 ID 重复出现 | 按 NFKC、空白归一化后的正文去重，候选扩取后再选取结果 |
| 旧测试数据包含长串 x 和重复标题 | 7 条已确认的 default 空间测试片段备份后标记 `metadata.retrieval_excluded=true`，检索和统计排除；上传与召回同时校验低质量内容 |
| 任意 Elasticsearch 错误触发静默关键词回退 | 错误向业务层报告；仅未配置远程向量模型时明确使用短语词法检索，不把本地哈希向量当语义向量 |
| 文档缩短后保留旧分片 | 全部分片嵌入和写入成功后，按空间与文档 ID 清理不再属于当前版本的分片；存储 ID 包含空间摘要 |
| 全部候选写入结果 citations | `data.retrieval_candidates` 保存候选，`retrieval_version=2` 标记新记录，`citations` 只保留最终正文实际标注的已检索来源；审核修订后重新筛选 |
| 自包含摘要也检索企业制度 | “仅根据以下/所给事实”等显式输入限制跳过检索，产生 `knowledge.skipped` 事件 |
| 历史页面和导出展示无关来源 | Java 公共任务读取及导出按正文标注筛选来源；React 不再回退合并全部节点候选。数据库快照、审计事件和报告正文保持原样 |

## 模拟业务数据

`docs/fixtures/business-knowledge.json` 包含 5 份明确标注模拟的“星河科技”制度：差旅报销、年假、采购审批、客户数据安全、新员工入职。每份都有 `metadata.simulated=true`，用于开发演示，不能当作真实企业政策。

导入 default 空间的文档 ID 为 `default_sim-*-2026`。旧片段备份为 `deploy/backups/knowledge-fixtures-20260913T175832199212Z.json`，包括完整 `_source` 与向量。备份目录已被 Git 忽略，原测试片段没有删除。其他空间未做批量清理。

复现数据修复（默认只读检查；`--apply` 才会备份、隔离并导入模拟制度）：

```powershell
py -3 -X utf8 deploy/repair-knowledge.py
py -3 -X utf8 deploy/repair-knowledge.py --apply
```

脚本使用现有 `deploy/.env`、`.env.r2` 和默认管理员登录，不打印凭证。备份恢复应按其中的 index、原 `_id` 和 `_source` 恢复指定条目，不重置整个索引。

## 参数与限制

当前 `qwen3.7-text-embedding-flash` 的这组样本中，正确结果的原始余弦相似度为 0.442 至 0.663；无关问题最高为 0.380。默认 `KNOWLEDGE_MIN_SIMILARITY=0.42`、`KNOWLEDGE_SIMILARITY_WINDOW=0.12`，可在部署环境调整。Elasticsearch 返回的 `_score=(1+cosine)/2`，不能把页面分数直接当作余弦门槛。

可通过 `py -3 -X utf8 deploy/verify-knowledge.py --scores` 检查原始分数。更换向量模型、增加真实文档或业务领域后必须重新评估阈值；这 15 个样例不等于普遍准确率。当前未引入重排模型、文档 ACL、版本事务或 OCR/文件解析。

来源筛选验证的是“正文标注是否指向检索到的片段”，不证明正文推理必然正确。新任务优先使用 `[来源: chunkId]`，兼容历史 `[来源: 文档标题]`；同名文档历史标注只能定位到标题，无法自动恢复不存在的精确分片依据。
